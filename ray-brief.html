Guild Ranks · engineering brief

Activation web app

Replace the activation Google Form with an Apps Script web app, so a member sees their new rank and rolls the d20 on screen instead of getting a fixed "response recorded" message.

Scope

Activation only. The signup form stays a Google Form and keeps working exactly as it does — don't touch it. This replaces the one screen a member sees after scanning a card.

Everything else stays put: same spreadsheet, same tabs, same columns, same card codes, same rules. If this project ends up changing the sheet's schema, something has gone wrong.

Why it exists

Google Forms confirmation screens are static text. The form can't know whether the script accepted or refused the scan, so it tells everyone the same thing. Staff currently have to look at the spreadsheet to find out what happened.

The level-up moment is the payoff of the whole scheme — it's what makes people bother activating at all. Right now it lands as a receipt.

There's a clickable prototype of the intended experience in webapp/index.html. Lift the UI from it freely; it was built for this. Note that its validation logic is a browser-side copy for demo purposes — the real rules live server-side, see below.

Architecture

An Apps Script project bound to the existing Loyalty spreadsheet, deployed as a web app. No external hosting, no new accounts, no new platform.

doGet(e)Serves the page. Reads the card code from e.parameter.c, which is what the QR carries. Should render the "activate this card" screen with the code already in hand — never ask the member to type it.
google.script.runClient calls the server to submit the email. Use withSuccessHandler / withFailureHandler. A form POST works too; either is fine.
validate(code, email)Already written, already tested. Call it. Do not reimplement it.

Reuse the existing validator

Code.gs already contains a validate(code, email) function, deliberately separated from the form-handling wrapper so it can be called from anywhere. It performs the four checks, writes both records on success, and returns: 

{ result: "activated" | "rejected",
  reason: "Promoted to level 4" | "Cannot skip levels — ..." }

It has 19 tests against it in google-sheets/test_code.js. Reimplementing the rules in the web app would give the scheme two sources of truth that will drift, and the drift will show up as members being promoted when they shouldn't be.

You will need a little more back than it currently returns — the member's name and their new level, to render the screen. Extend the return value; don't fork the logic. Update the tests to match.

The rules, for reference

  1. Does this card code exist? No → reject.
  2. Has it already been activated or voided? Yes → reject.
  3. Is this email a registered member? No → reject.
  4. Is the member at exactly card.level - 1? No → reject.

A rejection must leave Members and Cards completely untouched, and write one row to the Activation log explaining why. That property is what makes a mis-scan free.

Concurrency

Keep the LockService lock around activation. Two people scanning at the same moment must not both succeed — single-use codes are the whole security model, and Sheets reads are not atomic.

Screens

StateShows
arriveRank the card grants, one email field, activate button. Code carried invisibly.
activatedBig rank numeral, rank name, "roll for loot" and the d20. This is the moment — give it room.
refusedPlain "ask a member of staff", the reason, and reassurance that the card wasn't spent.
no codeSomeone opened the bare URL. Explain they need to scan a card.

Design for a phone, at night, on bar wifi. Assume a slow connection and a cracked screen. The d20 roll can be client-side and cosmetic — it doesn't affect rank, so it needs no server call.

Deployment

The trap that kills printed cards

A web app's URL contains its deployment ID. Creating a new deployment mints a new URL — and every card already printed points at the old one. That is an unrecoverable reprint.

To ship changes, always: Deploy → Manage deployments → (pencil) Edit → Version: New version → Deploy. That publishes new code at the same URL.

Only ever create a second deployment deliberately, for a test URL that no card points at.

Access settings

Execute asMe — the script needs the owner's rights to write to the sheet.
Who has accessAnyone — not "Anyone with a Google account". Members are standing at a bar; requiring a Google sign-in will kill activation rates and exclude anyone not signed in on their phone.

"Execute as me" plus "anyone" means an anonymous visitor runs code with the owner's sheet access. That's expected here — but it's also why the four checks matter. Treat e.parameter.c as hostile input: it's whatever someone typed into a URL bar. Never interpolate it into anything without escaping.

Acceptance criteria

Not done until all of these hold:

  1. Scanning a valid level 1 card as an unranked member promotes them and shows the rank screen with the d20.
  2. Scanning the same card again is refused, with the reason on screen.
  3. Scanning a rank more than one above the member is refused as level-skipping.
  4. An unregistered email is refused and told to sign up.
  5. A made-up code in the URL is refused.
  6. Every one of the above writes exactly one Activation log row, and refusals change nothing in Members or Cards.
  7. node google-sheets/test_code.js still passes after any change to the validator.
  8. The page works on a phone, and on the venue's actual wifi.

Timing — this is on the critical path

The QR codes currently point at the Google Form. Switching to the web app means every card's QR has to be regenerated against the new URL.

That is free today and a full reprint after the cards are printed. So the deployment URL is needed before the print run, not after.

Send the /exec URL over as soon as the app is deployed, even if the UI isn't finished. Regenerating takes ten seconds and the card codes themselves never change, so it can happen in parallel with the rest of the build.

One thing worth raising early

Apps Script web app URLs are long, which makes a dense QR — the same problem the Google Forms URL has. A short domain redirecting to /exec would fix both, and let the printed code stay at 20mm instead of 25mm. About £12 a year. Worth deciding before the artwork is final.

What to send back

  • The deployed /exec URL — first, and before the UI is polished
  • Confirmation of the six acceptance tests, particularly the refusals
  • Whether you extended validate(), and that the test suite still passes
  • A note on whether the signup form stays a Google Form — it should, but say so if you disagree

If anything here conflicts with what's already in the sheet, the sheet wins — it has real structure Reza built and tested. Flag the conflict rather than changing the schema around it.
